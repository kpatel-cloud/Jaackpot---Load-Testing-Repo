JAACKPOT Real Load Testing Guide Using JMeter  1. Purpose  This document explains how to perform an approved real load test for the JAACKPOT application using Apache JMeter.  JAACKPOT is a real-money Bitcoin casino platform with a public player-facing application and an internal Backoffice used by Support, Finance, Risk Management, and Operations teams. Because the platform involves BTC deposits, wagers, withdrawals, account activity, and internal operational workflows, load testing must be controlled, monitored, and approved before execution.  This guide is written for a real JMeter execution using approved test credentials.  Recommended Real Load Testing Workflow  The recommended workflow is not to manually add every API inside the JMeter GUI.  Use Postman/YAML as the maintainable source and generate/update the JMeter .jmx from it.  Postman API Collection  -> Export collection and environment JSON  -> Group APIs into business flows  -> Maintain readable YAML flow spec  -> Generate or update JMeter .jmx  -> Run 1-user smoke test  -> Fix token extraction, dynamic IDs, assertions, and timers  -> Run approved load test  -> Generate JMeter report  File responsibility:  ΓùÅ   Postman collection: raw API source.  ΓùÅ   YAML flow spec: readable test design and review document.  ΓùÅ   Generated JMeter .jmx: executable load testing file.  ΓùÅ   CSV data files: approved test users and test data.  ΓùÅ   JMeter reports: performance results and evidence.  This keeps the test plan maintainable. The team reviews YAML, while JMeter executes the generated .jmx.  Recommended folder structure:

JMeter Test Plan Components  Each test plan should include:  JMeter Script Architecture  The JAACKPOT load test will be implemented as structured JMeter .jmx test plans. These test plans will model approved API-level user journeys using Thread Groups, HTTP samplers, variables, timers, extractors, assertions, and reporting outputs.  The test suite should be modular so each critical business flow can be executed independently or as part of a combined load profile.

Recommended script modules:  ΓùÅ   Authentication module: logs in using approved test credentials, captures token/cookie values, and prepares the authenticated session.  ΓùÅ   Read API module: executes public and authenticated read APIs such as game list, profile, wallet balance, and transaction history.  ΓùÅ   Wallet module: validates wallet balance, deposit status, and controlled withdrawal-related APIs where approved.  ΓùÅ   Wager module: validates game launch, wager placement, settlement, balance refresh, and bet history using controlled test funds. Final JMeter report is generated from merged results.  Cloud vs On-Prem Worker Placement  For a 10,000-user load test, cloud worker nodes are usually the better option.  Recommended default:  Use cloud instances as JMeter workers.  Run traffic through the same public path real users use:  CDN/WAF -> Load Balancer -> Application/API.  Cloud workers are preferred because:  ΓùÅ   They can scale horizontally quickly.  ΓùÅ   They provide predictable CPU, memory, and network capacity.  ΓùÅ   They avoid office/on-prem bandwidth limits.  ΓùÅ   They allow multiple geographic regions if needed.  ΓùÅ   They can be created and destroyed after the test.  ΓùÅ   Their public IPs can be allowlisted in WAF/CDN rules.  On-prem machines are suitable only when:  ΓùÅ   Testing small smoke or baseline traffic.  ΓùÅ   Testing an internal-only environment.  ΓùÅ   Testing from a specific corporate network path.  ΓùÅ   Client policy does not allow cloud load generators.  ΓùÅ   Network team wants to validate office/VPN route capacity.  On-prem is usually not suitable for 10,000-user testing because:  ΓùÅ   Office internet bandwidth may become the bottleneck.  ΓùÅ   NAT/firewall limits may be hit.  ΓùÅ   Results may reflect local network constraints instead of application capacity.  ΓùÅ   Scaling machines is harder.

ΓùÅ   Monitoring and repeatability are weaker.  Should Workers Be On The Same Network?  Not always.  For production-like public testing:  Workers should generally NOT be inside the same private network as the application.  Reason:  ΓùÅ   Real users access through public internet, CDN, WAF, and load balancer.  ΓùÅ   Placing workers inside the same private network may bypass important production controls. ΓùÅ   Public API traffic.  ΓùÅ   CDN/WAF behavior.  ΓùÅ   Realistic internet path performance.  ΓùÅ   Campaign or event traffic readiness. ΓùÅ   The client wants to isolate application capacity from internet/CDN latency.  ΓùÅ   Testing internal services through VPN, VPC peering, private link, or bastion routing.
